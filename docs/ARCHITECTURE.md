# Architecture

Timeline is a decoupled **React SPA** talking to a **Django REST Framework** API over JWT,
backed by **PostgreSQL**. In production a single nginx origin serves the built SPA and
reverse-proxies the API.

```
Browser ── React SPA (Vite build) ──┐
                                     │  /api  (JWT: Authorization: Bearer …)
                                     ▼
                      nginx ──► gunicorn ──► Django + DRF ──► PostgreSQL
                      (prod)     (/api, /admin, /static, /media)
```

In **dev**, the Vite dev server (`:5173`) proxies `/api` to the Django dev server
(`:8000`); in **prod** everything is one origin behind nginx (`:80`), so there is no CORS.

## Tenancy model

The core of the app is per-project isolation:

```
User ──< ProjectMembership(role) >── Project ──< Category
                                          └────< Event
```

- A **Project** has many members through **ProjectMembership**, which carries a `role`
  (`owner` / `editor` / `viewer`).
- **Category** and **Event** each have a non-null `project` FK. There is no global data —
  every row belongs to exactly one project.
- A user can only see/act on projects they're a member of. This is enforced in **two**
  places (never one):
  1. **Queryset filtering** — `get_queryset()` filters to the caller's projects, so other
     projects' rows are invisible (a list is empty, a detail is 404).
  2. **A DRF permission class** — object-level checks on top of the filter.

### Data model (`backend/projects/models.py`, `backend/events/models.py`)

| Model | Key fields |
|-------|-----------|
| `Project` | `name`, `description`, `owner→User`, `members (M2M through ProjectMembership)` |
| `ProjectMembership` | `user→User`, `project→Project`, `role`, `joined_at` — `unique(user, project)` |
| `Category` | `project→Project`, `name`, `color` — `unique(project, name)` |
| `Event` | `project→Project`, `title`, `start`, `end`, `category` (string), `color`, `notes`, `percent_complete`, `depends_on (self M2M)` |
| `ProjectTemplate` | `owner→User`, `name`, `description`, `categories (JSON)`, `tasks (JSON)` |
| `Team` | `owner→User`, `name`, `description`, `members (M2M → User)` |

`Event.category` is a **free-text string** (not an FK). The frontend groups events into
"tracks" by category name; the `project` FK is the real security boundary, so a string
label is enough and keeps the wire format simple.

## Authentication

JWT via `djangorestframework-simplejwt` (access + refresh).

- `POST /api/auth/register/` — open self-registration (creates a hashed-password user).
- `POST /api/auth/token/` — returns `{access, refresh}`.
- `POST /api/auth/token/refresh/` — rotates the access token.
- `GET /api/me/` — the current user.

**Frontend** (`frontend/src/auth/`, `frontend/src/api.js`):

- `tokenStore.js` persists tokens in `localStorage` (single module → swappable).
- `AuthContext` bootstraps the session from a stored refresh token on load, exposes
  `login/register/logout` and the current user.
- `api.js` attaches `Authorization: Bearer <access>`; on a `401` it transparently calls
  the refresh endpoint **once** (single-flight, so concurrent calls share one refresh) and
  retries; if refresh fails it clears tokens and redirects to `/login`.

Because the API is JWT-in-header (not cookies), CSRF doesn't gate `/api`. Django's session
+ CSRF still protect `/admin`.

## Permissions (`backend/projects/permissions.py`)

A role-tiered permission class reads the project id from the nested URL:

- not authenticated → deny
- not a member → deny (and the queryset filter makes data invisible)
- safe methods (`GET`/`HEAD`/`OPTIONS`) → any member (viewer+)
- writes to events/categories → editor+
- member management, `add-team`, project delete → **owner only**

Role tiers: `viewer < editor < owner`.

## API routing (`backend/projects/urls.py`)

Routes are **nested per project** via `drf-nested-routers`, so the project id is always in
the path (it can never be a forgotten/forgeable query param):

```
/api/projects/<id>/events/        /api/projects/<id>/categories/
/api/projects/<id>/members/       /api/projects/<id>/add-team/
/api/templates/  /api/templates/instantiate/
/api/teams/      /api/teams/<id>/members/
```

The OpenAPI schema is generated by `drf-spectacular` and served at `/api/schema/`,
`/api/docs/` (Swagger), and `/api/redoc/`.

## Templates

A template is `{categories, tasks}` where each task stores **relative** timing
(`start_offset_minutes`, `duration_minutes`) and `depends_on` as task indices. Built-in
templates live in code (`backend/projects/templates_builtin.py`); saved templates store the
same shape as a `ProjectTemplate` row — so instantiation treats both identically. On
**instantiate**, tasks are shifted so the first lands on the chosen start date, dependencies
are re-wired, and the project is created for the chosen owner.

## Teams

A `Team` is a user-owned, flat list of users. Adding a team to a project is a **one-time
snapshot**: each current member gets a `ProjectMembership` at the chosen role
(idempotent — existing members are untouched). The team↔project link is not persisted;
editing the team later doesn't change projects it was already added to.

## Frontend architecture

- **Shell** (`App.jsx`) = `AuthProvider` + `ToastProvider` + router. Routes: `/login`,
  `/register` (public), `/` (dashboard), `/teams`, `/projects/:id` (timeline, lazy-loaded),
  `*` (404). `ProtectedRoute` gates authenticated routes with a loading gate + deep-link
  return-to.
- **`ProjectTimeline`** loads a project's events/categories, derives `canEdit` from the
  caller's role, and renders the timeline read-only for viewers.
- **`Timeline` performance** (it re-renders on every mouse move / zoom):
  - the **critical-path (CPM)** analysis is memoized on `events` only (not zoom), separate
    from the cheap arrow-geometry memo;
  - per-track maps are memoized so `EventBlock`'s `React.memo` actually caches;
  - the cursor label updates the DOM imperatively (no re-render per mouse move);
  - **zoom** eases toward its target via a single `requestAnimationFrame` loop, and
    re-anchoring runs in `useLayoutEffect` (before paint) so it glides instead of snapping;
  - the ruler bounds its tick count, and a project fits its zoom on load — so even a
    multi-year project renders instantly.
- **`Minimap`** draws the whole project to a canvas and overlays a draggable viewport box.

## Request flow (example)

`Editor drags an event` →
`PATCH /api/projects/42/events/7/ {start, end, category}` →
JWT auth → `IsProjectMember` (editor+ for a write) → `EventViewSet` queryset scoped to
project 42 → `EventSerializer` (validates `end > start`, `depends_on` within the same
project) → DB update → optimistic UI confirms.
